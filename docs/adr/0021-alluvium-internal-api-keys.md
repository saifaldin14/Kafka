# ADR-0021: Alluvium-internal API keys

- **Status:** Accepted
- **Date:** 2026-11-23

## Context

Several enhancements need requests between Alluvium nodes that Kafka has no API for: elastic partitions, diskless topics, tenancy and the autopilot (the `foundation-for:` labels of PROTO-F15). Under [ADR-0010](0010-alluvium-is-its-own-platform.md), a Kafka client must never notice them. Three things have to be fixed before the first one is written: which API keys they use, where their schemas live, and how they stay invisible to Kafka clients.

What Kafka 4.4.0 does:
- It numbers its APIs from 0 upwards, one at a time. In 4.4.0 the keys run from 0 to 94 ([`ApiKeys.java`](https://github.com/apache/kafka/blob/4.4.0/clients/src/main/java/org/apache/kafka/common/protocol/ApiKeys.java)). The key is an `int16`, so keys above 32767 can't exist.
- A request whose key it doesn't know fails in `RequestHeader.parse` (`ApiKeys.forId` throws). A key that isn't enabled on the listener fails in `Processor.parseRequestHeader`. Either way the connection is closed without a response ([`RequestHeader.java`](https://github.com/apache/kafka/blob/4.4.0/clients/src/main/java/org/apache/kafka/common/requests/RequestHeader.java), [`Processor.java`](https://github.com/apache/kafka/blob/4.4.0/server/src/main/java/org/apache/kafka/network/Processor.java)).
- `ApiVersions` lists only the APIs enabled on the listener.

Alluvium already generates `ApiKey` from Kafka's schemas. A test checks it against Kafka's recorded registry, and `advertised_api_versions` builds the ApiVersions response from it alone (PROTO-F07).

## Decision

1. **The reserved block is API keys 32000 to 32767**, the top of the positive `int16` range.
   - At Kafka's pace of a few new keys a year, it won't reach 32000.
   - Negative keys are not used. Kafka's `RequestHeader.parse` and Alluvium's header errors both use −1 for "no key read".
   - Key 32000 is reserved for `AlluviumApiVersions`, the internal counterpart of ApiVersions (point 4). It is added with the first internal API.
2. **Internal schemas live in `schemas/alluvium/messages/`**, in Kafka's JSON schema format, and are generated by the same rules as Kafka's.
   - `cargo xtask codegen` writes them to `crates/alluvium-protocol/src/internal/`, apart from `generated/`. So `ApiKey`, its parity test and `advertised_api_versions` never include them.
   - Codegen fails on any of these:
     - a request or response whose key is outside the block;
     - a key Kafka's schemas use, removed APIs included;
     - two internal requests, or two internal responses, with the same key;
     - a request without a response, or a response without a request, as Kafka's generator requires;
     - a schema, data schemas included, that isn't flexible in every version.
   - These rules also hold for a retired schema, one without valid versions, so a retired API keeps its key.
   - These schemas are Alluvium's own. Their generated files carry no Apache notice, unlike the files generated from Kafka's schemas.
3. **Versioning.**
   - Every internal API is flexible from version 0 (`"flexibleVersions": "0+"`). It therefore uses request header v2 and response header v1, and can gain fields as tagged fields without a new version.
   - Versions only grow. A release supports every version the previous release sends, so a rolling upgrade never strands a node.
   - A version is removed only in a release after one in which no node sends it.
4. **Internal APIs are never advertised to Kafka clients.**
   - ApiVersions responses list Kafka's APIs only, exactly as Kafka 4.4.0 would on that listener.
   - Alluvium nodes learn each other's internal versions from `AlluviumApiVersions`.
   - Advertising internal APIs in ApiVersions, even only to Alluvium peers, would make the response depend on who asks. It would also break the differential test against Kafka (PROTO-0156).
5. **Internal APIs are never accepted from Kafka clients.** A request with an internal key is refused in two cases: it arrives on a listener that isn't inter-node, or it comes from a principal that isn't an internal (inter-node) principal. Either way it is treated exactly as Kafka treats an unknown key: the connection is closed without a response. An `internal_api_rejected` event records it (PROTO-0155).

## Consequences

- A Kafka client can't tell Alluvium's internal APIs exist. An ApiVersions response is the same as Kafka's, and a probe with an internal key is answered as Kafka answers any unknown key.
- Internal APIs get the generated codec, golden output, round-trip tests and decode limits that Kafka's APIs get. PROTO-0154 adds the codegen checks. A sample request and response in `schemas/alluvium/test/` are generated into the test-only `test_messages` module, so a change to how internal APIs are generated shows as a reviewable diff.
- The request router (PROTO-0155) must look up internal keys in a table of their own, after the listener and principal checks.
- Fuzz targets for internal schemas come with PROTO-0156.
- If Kafka ever allocated keys near 32000, codegen would fail on the collision, and a new ADR would move the block.

## Alternatives considered

- **Keys just above Kafka's, such as 1000 and up.** Kafka could reach them. Every new Kafka key would then need checking against Alluvium's, and a collision would be a protocol incompatibility.
- **Negative keys.** They don't collide with Kafka. But −1 already means "no key read" in Kafka's header parsing and in Alluvium's errors, and a block of negative keys would put internal APIs next to that sentinel.
- **A separate port or protocol for inter-node calls.** It would duplicate the framing, authentication, quotas and observability that the Kafka protocol path already provides, for no gain in isolation over the listener and principal checks.
- **Advertising internal APIs in ApiVersions only to Alluvium peers.** The response would depend on who asks, and a client could ask as a peer. An internal versions API keeps the Kafka-facing response fixed.
